# Architecture

This document describes how kdlock works as written in this directory. It is
the reference for the code in `kernel/` and for the contract the translator in
`jit/` must meet. What has run and been measured:
[BUILD_AND_TEST.md](BUILD_AND_TEST.md) and `bench/results/kdclaude/`.

## 1. Goal and mechanism

A contended lock is the place where the lock holder can do the waiters' work
cheaply: the protected data is already in its cache. TCLocks does this by
letting the holder (the *combiner*) switch its stack pointer to a waiter's
saved stack and run the waiter's critical section. It cannot do it for code
that depends on the running task (`current`, the stack canary, the top of
stack), because those are read through `%gs` and `%gs` still belongs to the
combiner.

kdlock keeps the TCLocks mechanism and changes what the combiner runs: not the
waiter's original code but a **relocated copy** generated by a userspace
translator. In the copy, the few task-identity accesses read the waiter's
values. Anything the copy cannot execute correctly ends it with an *exit*,
and the waiter then continues natively from exactly that instruction
(*handback*). Delegation is therefore always optional: a section that cannot
be delegated is simply run by its owner.

Delegation is also only used where it pays. A spinlock or mutex is in
**plain mode** until its queue is deep: a contended caller then waits exactly
as on the native lock, on its own stack, and publishes nothing. Queue heads
measure the queue and switch the lock to **delegation mode**, and combiners
switch it back (section 7a).

Terms: **origin** (W) is the task whose critical section is being run;
**executor** (C) is the CPU/task that runs it; the **session** is one
combiner's run over a queue; a **packet** (`struct kd_regs`) is the
continuation state of an origin; a **site** is the return address of a
lock call, i.e. one place in the kernel that takes a lock; an **image** is
the generated copy for one site.

## 2. Components

```
 kernel (built in, CONFIG_KDLOCK)                       userspace
 ┌───────────────────────────────────────────┐         ┌──────────────────────┐
 │ kd_entry.S   entry stubs, resume, jit      │         │ jit/kd_daemon.py     │
 │ kd_core.c    wait, session, executor       │ events  │  event loop          │
 │ kd_spinlock/rwlock/mutex/rwsem.c  families │───────► │  cumulative knowledge│
 │ kd_image.c   sites, images, event ring     │         │ jit/kdjit/translator │
 │ kd_dev.c     /dev/kdlock, debugfs stats    │◄─────── │  capstone, relocation│
 └───────────────────────────────────────────┘ images  │ jit/kdjit/kernel.py  │
                                                        └──────────────────────┘
```

* Kernel side is built into the kernel. It must be: generated code addresses
  per-CPU state with a 32-bit `%gs`-relative displacement, which only
  built-in per-CPU data permits, and the locks are used from early boot.
* The translator is a userspace program. It reads kernel text through
  `/dev/kdlock`, builds an image per site, asks the kernel for executable
  memory, links the image for that address and loads it. The kernel never
  waits for it.

## 3. Lock objects

All four families share one 4-byte queue word `struct kd_qlock` and one set of
queue primitives in `kd_internal.h`. Its layout is that of the native queued
spinlock: a `locked` byte (held, plus the holder-owned mode bit
`KD_Q_DELEG`), a second byte that is the `pending` bit for the spin class
and the `flags` (`SLEEPERS`, `HANDOFF`, `DELEG`, `XHEAD`) for a mutex, and a
16-bit MCS tail.

| Object | Size | Layout |
| --- | ---: | --- |
| `struct kd_spinlock` | 4 | the queue word is the lock |
| `struct kd_rwlock` | 8 | qrwlock-style count (writer byte, writer-waiting bit, reader count) + queue word `wait` |
| `struct kd_mutex` | 32 | queue word (`locked` is the lock, flags `SLEEPERS`/`HANDOFF`), `wait_lock`, `owner`, `waiters` list |
| `struct kd_rwsem` | 40 | `count` (writer bit, waiting writer, need-wake, reader bias) + a `kd_mutex m` used as the queue |

The sizes equal the native ones, so containers that embed locks
(`struct page`, `lockref`, ...) keep their layout.

Queue nodes (`struct kd_node`, one cache line) live in per-CPU arrays:
spin-class nodes are a per-CPU LIFO stack, sleepable-class nodes are
allocated from a FREE-state pool. Four nodes per CPU and class
(`KD_MAX_NODES`); when they run out the caller waits without queueing.
Node states: `FREE, WAIT, HEAD, HEAD_D, RESUME, ABANDON, HWAIT, HBACK, DROP`
(`RUN` is no longer used).

Where the per-CPU state sits matters for the plain path (measured, see
`bench/results/kdclaude/README.md`): everything other CPUs write (nodes, the
packet) is in 128-byte blocks apart from what only the owner writes; the
count of nodes in use, the plain-wait statistic and the mode memory are in
the first node's own line, as the native lock keeps its node count; and the
sampling counter is deliberately *not* in that line.

The per-site record (`struct kd_site`) is two cache lines for the same
reason. Every contended caller reads its first line (`rip`, `entry`); the
combiner writes the counters in the second once per section. As one
72-byte object from the 96-byte slab it began at offset 0 or 32 of a line,
and at 0 the counters shared the line with `rip` and `entry`: each section
then took that line from every waiter reading it. Which offset a site got
was decided at allocation, so each site ran at one of two rates per boot
(kd spin c01 at 32 workers, 2.7 GHz: 6.4-6.5 Mops/s in builds #67 and #68,
4.4 in #69, with the same session code). That was the boot-to-boot
difference of rounds 7 and 8; rounds before the split (build #70) carry it.

## 4. The contended acquisition, step by step

### 4.1 Entry stub (`kd_entry.S`)

Every delegable entry (`kd_spin_lock*`, `kd_write_lock*`, `kd_mutex_lock*`,
`kd_down_write*`) is an assembly stub, not a C function, so that it can see
and save the caller's registers.

1. **Fast path.** One cmpxchg on the lock word. On success it adjusts
   preempt count / IRQ / BH state as the native API would and returns. No
   packet, no stack switch.
2. **Slow function.** On failure the stub calls the family's C `*_slow`
   function on the caller's own stack, passing the return address (the
   *site*). In plain mode that function does the whole contended
   acquisition and the stub returns: this is the non-delegating path, and
   for the spinlock it is the native queued-spinlock algorithm (pending
   waiter, MCS queue, head takes the lock with a plain store). A C call
   preserves the callee-saved registers and the stack pointer, so nothing
   is lost if the function instead reports "publish".
3. **Offer path.** The function reports that when the lock is in delegation
   mode and this caller can publish (task context, `kd_cpu.busy` clear, the
   site has an image). The stub then sets `busy` with a single non-locked
   `bts` (an interrupt on the same CPU sees it atomically), stores the
   caller's continuation into this CPU's packet (callee-saved registers,
   `rsp`, return `rip`, flags), switches `rsp` to the per-CPU **wait stack**
   (16 KiB) and calls the C wait function. From here the caller's own stack
   is untouched and unused: that is what lets another CPU run on it.

### 4.2 Waiting with a published continuation (`kd_wait_spin`, `kd_wait_sleepable`)

The waiter queues a **delegable** node (`entry` = image entry, `regs` =
packet). A site without an image is counted instead; at 64 contended waits
(`KD_REQ_THRESHOLD`) a `KD_EV_REQUEST` event asks the translator to build
one, and until then its callers wait without publishing.

Once queued, a spin-class waiter demotes its packet and the top of its
stack from its private caches to the shared level (`CLDEMOTE`,
`kd_cldemote`, a no-op on CPUs without it): the combiner is the next to
touch them. Measured (builds #67 and #70, in-boot A/B, 3 rounds): spin c01
and rwlock writers +1 to +3% from 8 workers, spin c08 -0.2 to +1.3%. The
sleepable class gains nothing (mutex c16 loses up to 2.7%), so it does not
demote. The effect is small because the combiner already requests the
packet one section ahead; the combiner demoting the lines back after a
section loses 3 to 20% and was not kept.

The node is appended with one `xchg` on the queue tail. A node with a
predecessor spins on its own `state`:

* `RESUME` — a combiner already executed this waiter's section; the waiter
  returns `KD_WAIT_RESUMED`.
* `HEAD` / `HEAD_D` — it is now the queue head: it takes the lock itself.
  `HEAD_D` says the lock is in delegation mode (spin class; a mutex keeps
  its mode in a flag).

### 4.3 The queue head becomes the combiner

The head takes the lock, runs the family's `post()` hook (rwlock: wait for
readers; rwsem: set the writer bit and wait for readers), and, in delegation
mode, runs a **session** (`kd_session`):

```
while the next node n exists and the budget is not exhausted:
    stop if n has no image, need_resched(), or the mutex HANDOFF flag is set
    if NUMA order is on and n is on another node: defer it (see 7)
    stop if n's saved interrupt state is incompatible with ours
    sleepable class: n was announced (claim = true) during the previous
        section; barrier, then read n.state; if the waiter withdrew, unlink it
    sleepable class: announce the waiter after n (LOCKS 4)
    prefetch the next waiter's node and packet
    done = kd_exec_one(root, n)          # run n's section, section 5
    unlink n from the queue
    publish n.state = RESUME              # last access to n and its packet
    stop if the section was handed back (done == false)
    every 32 sections: leave delegation mode if the queue got short (7a)
```

After the session the head runs the family's `release()` hook if the queue
word is only a wait lock for that family, promotes its successor
(`kd_q_pass`) and returns `KD_WAIT_LOCAL`: the stub then lets the head run
**its own** critical section natively. Because the head took the lock before
the session and keeps it throughout, the order of sections is: delegated
waiters first, its own last.

### 4.4 Waiter resume

On `KD_WAIT_RESUMED` the stub calls `kd_finish_resume(pin)`: it disables
interrupts, applies the preempt-count change the section caused
(`pc_delta`) and installs the packet's logical registers and flags with
`kd_resume`, which switches back to the original stack and returns to the
instruction **after the section's release call**. The origin never runs the
section and never executes the release.

## 5. Running a section (`kd_exec_one`)

The executor prepares and enters generated code:

1. `local_irq_save`; if the origin had softirqs off, BH off as well.
2. Add `KD_EXEC_PIN` (32) to the preempt count. A section may release locks
   the origin took earlier (nested, non-LIFO); the pin keeps the count from
   reaching zero on the executor.
3. Fill `kd_cpu`: `task` (origin), `canary`, `stack_top`, `root` (the lock
   being served), `cur` (the packet), `anc` (number of outer roots).
4. `kd_jit_enter(packet, entry)` loads the packet's registers, installs the
   origin's logical flags with `popfq`, switches `rsp` to the origin's stack
   and jumps into the image. Execution is real machine code on the origin's
   real stack.

The image leaves through an **exit stub** (`mov` only, to
`gs:[kd_cpu.exit_ip / resume / exit_code / aux]`, then `jmp kd_jit_exit`).
`kd_jit_exit` saves the full state back into the packet and returns to
`kd_exec_one`, which decides by exit kind:

| Exit | Meaning | Action |
| --- | --- | --- |
| `UNLOCK` | the section called the release of the **session root** | do not release; record its effects on the origin (`kd_apply_unlock`: preempt count, IF, BH) in the packet; the section is complete (`KD_STOP_DONE`) |
| `UNLOCK` with a downgrade of the root (rwsem) | the section goes on as a reader | `kd_vdown=1`: keep the write side, mark the packet (`vdown`) and continue in generated code; the root's `kd_up_read()` then completes the section. A handback while marked performs the downgrade first (LOCKS 5). `kd_vdown=0`: hand back |
| `UNLOCK_ANC` | release of a non-root lock while outer sessions exist | if the lock is an outer root: mark `released`; else perform the release natively and continue |
| `NESTED` | a contended inner spin-class lock inside the section | acquire it recursively (section 8) |
| `ACQUIRE` | a sleeping-family acquire (mutex, rwsem) inside the section | try to take it as the origin without sleeping; else hand back |
| `MISS_CODE / MISS_IND / MISS_RET` | unknown direct target / indirect target / return target | report to the translator, hand back |
| `FRONTIER` | instruction or callee only the origin can run (extable instruction, privileged instruction, scheduler entry, user copy, unknown text) | hand back |
| `BUDGET` | translator budget exhausted | hand back |

Afterwards the executor measures the preempt-count delta, subtracts it from
itself and adds it to the packet (`pc_delta`), restores IF/BH, and returns.

### Handback

The packet holds the first instruction the executor did **not** execute. The
lock word stays "held" and now **belongs to the origin**: the combiner does not
release it. The node is resumed, the origin continues natively from the exit
point (every effect of the executed prefix stays, nothing is replayed), and
later releases the lock with the ordinary unlock. Handback is a plain
ownership transfer, which is why it is cheap and exact. Every call that can
switch tasks (`schedule` and its relatives, `yield`, the sleeps) is a
frontier, so a section that would block is always back on its own task
before it does.

A section can be handed back with interrupts off and an interrupt-safe
lock held, and that lock can belong to the executor's CPU, because the
copy's per-CPU accesses are the executor's (a wakeup takes the executor's
runqueue lock and its hrtimer base lock). The executor therefore keeps its
own interrupts off until it has published the resume (`kd_irq_release()`).
Before build #65 it enabled them first, and a timer interrupt in that
window waited for a lock the origin could not release, as it was never
resumed (`bench/results/kdclaude/mmap1-20261115-64cpu/`).

Families where the queue word is only a wait lock (`keeps_q`: rwlock, rwsem)
transfer the grant (writer byte / writer bit) but not the queue word.

### Role exchange

What the combiner C does after a handback depends on `kd_xchg` (default 1:
mutex and rwsem writer; 2: every family; 0: never).

Without an exchange C stays queue head, waits for the origin W to release,
takes the lock again and continues its session.

With an exchange the roles swap. C's node already publishes C's own
continuation, so C **offers itself** before it resumes W: the node goes to
state `HWAIT` and is entered in a small table keyed by lock address. C is
then a delegable waiter at the front of the queue. When W releases the lock
it **takes the head role over** (`kd_release_combine`): it links a node of
its own in front of C's and runs a session, which serves C first and then
the rest of the queue; afterwards it passes the head role on and releases.
The lock's data moves to W's CPU once and stays there.

* W learns of the offer without reading the lock word before its release
  (that read can cost a cache transfer on the handover path). A spin-class
  holder cannot leave its CPU: the offer is counted in its packet and, when
  it resumes, in `kd_cpu.xcount`, which its releases test. A mutex or rwsem
  holder may move: its packet names the lock (`kd_cpu.xs_hint` on the CPU
  where it resumes), and elsewhere the release, a single atomic operation,
  finds the `XHEAD` mark in the value that operation returns and takes the
  lock again for the session if nobody was faster.
* An offer leaves `HWAIT` only under the table's bucket lock, in one of
  three ways: W took over (`WAIT`: C is an ordinary queued waiter), W
  declined (`HBACK`: its release runs where a session cannot, for example
  inside another delegated section or in a downgrade), or C withdrew
  (`HBACK`, sleepable class only: W stopped running or C's CPU is wanted).
  After `HBACK` C is queue head as without an exchange.
* While W has a spin-class offer to answer it does not publish its own
  continuation for another lock: the combiner that ran it would not know.

Measured effect (A/B in one boot, a sixteenth of the sections handed back):
see LOCKS.md 6a. It helps where the holder really blocks or the combiner
would otherwise sleep with the queue in its hands, and costs a few percent
where a handed-back section just finishes.

## 6. Context transfer

While a section runs on the executor:

* **Task identity.** Accesses to `current_task`, `__stack_chk_guard` and
  `cpu_current_top_of_stack` read `kd_cpu.{task,canary,stack_top}`. These are
  the only `%gs` accesses the translator rewrites. All other per-CPU accesses
  address the executor's own per-CPU area (see
  [DIFFERENCES.md](DIFFERENCES.md) D3).
* **Interrupt flag.** The executor installs the origin's logical IF with
  `popfq` on entry and reads it back with `pushfq` at the end. The executor
  never enables interrupts it had itself disabled: sections whose saved IF is
  on are not run by an executor that has interrupts off (`kd_ctx_compatible`).
* **Preemption.** Disabled for the whole section. The change in preempt count
  the section causes on the executor (including the lock it ends with) is
  undone locally and added to the origin on resume.
* **Logical task for lock functions.** Native lock functions called from a
  section (`kd_*`) act for the origin through `kd_logical_current()`: mutex
  owner, wake targets, etc.
* **RCU read-side nesting** (preemptible RCU). `rcu_read_lock()` and
  `rcu_read_unlock()` count in the task structure, and a task's count may
  only be changed by code running as that task, which includes the
  interrupt handlers on its CPU. The copy therefore calls
  `__rcu_read_lock()` / `__rcu_read_unlock()` natively, where they count for
  the executor, and the depth is carried like the preempt count: the packet
  says how many read-side sections the continuation is in (`rcu_depth`), an
  executor holds that many on top of its own while it runs it, and the
  origin brings its own count in line when it resumes, with real lock and
  unlock calls so that each task does its own exit processing
  (`kd_rcu_sync`). Before this, a delegated `rcu_read_lock()` section raced
  with the origin's interrupt handlers and the kernel reported an unbalanced
  depth (build #38).
* **Other state reached through `current`.** A read through `current` gives
  the origin's value. A non-atomic update of an origin task field from the
  executor's CPU has the hazard just described if interrupt handlers on the
  origin's CPU update the same field (`pagefault_disabled`,
  `migration_disabled` are the known candidates). Only the RCU depth is
  handled; see section 11.

## 7. NUMA order

As in TCLocks, a session serves only waiters of the combiner's NUMA node
(`node_id` of the CPU that queued the node). A delegable waiter of another
node is unlinked, still waiting, onto a session-private list, and the session
continues with the waiters behind it. At the end the list is spliced back
*in front of* the queue in its original order, so its first waiter is the next
head and combines for its own node. Passed-over waiters count against the
batch budget (`kd_batch`, default 4096) so handbacks cannot extend it;
waiters without an image are never passed over. `kd_numa=0` restores FIFO.

The batch was 1024 until build #68. Within one node its value does not
matter from 1024 up. Across two nodes every end of a session moves the
lock's data to the other node (64 workers, in-boot A/B, 4096 against 1024:
spin c01 +5.1%, rwlock writers +3.0%, rwsem writers +2.0%, mutex +1.2 to
+1.6%; 16384 under 1% more; 256 costs 10 to 17%). The TCLock backend of
the bench runs with 1024, its maximum, so kd's sessions are up to four
times as long as TCLock's in the comparisons from round 9 on.

A family can delay the deferral (`kd_family.numa_after`): the session then
serves that many waiters in queue order before it defers any. Only rwsem sets
it, to 32; the other families use 0. On 380G10 (build #49, in-boot
alternation, 3 rounds, 32 workers across two nodes), deferral from the
first waiter took writers-only rwsem from 1.56 to 3.56 Mops/s. The same
setting took 20% writes from 2.34 down to 1.82 Mops/s, because those
sessions serve only 6-11 writers before a reader phase. With 32, both
profiles kept the better value: w100 at 3.63, w20 at 2.31.

Consequence: a waiter is delayed by at most (batch × number of nodes ahead of
it) executions. This is a bound on batches, not a fairness guarantee for
arbitrary workloads.

`kd_numa_after` (default 32) is the value a family with `numa_after` set
uses, so it can be compared within one boot. Rechecked on build #74 (32
workers as 16+16, in-boot alternation): 0 against 32 is 1.00-1.02 for 1%
writes and writers only, 1.18 for c16 with 20% writes and 1.00 for c01; with
eras (7b) 0 gains nothing over 32 and loses 17% on c01 with 20% writes. It
stays at 32.

## 7b. Eras: readers and NUMA

The NUMA order above acts inside a session, so it reaches delegated writers
only. Readers are never delegated: each runs on its own CPU, writes the
reader count there and reads the protected data there. With the same 32
workers placed on one node or as 16+16 (`bench/run_place.py`, build #72):

| profile | Native | kd | TCLock |
|---|---|---|---|
| mutex, rwlock writers, rwsem writers | 0.52-0.58 | **0.95-0.97** | 0.97-0.99 |
| rwlock, 20% writes (c01 / c16) | 0.71 / 0.61 | 0.74 / 0.57 | 1.00 / 1.00 |
| rwsem, 20% writes (c01 / c16) | 0.64 / 0.62 | 0.63 / 0.57 | 0.71 / 0.71 |
| rwlock / rwsem, 1% writes | 0.80 / 0.79 | 0.83 / 0.88 | 0.83 / 0.83 |

Rate on two nodes over rate on one. Where every section is delegated kdlock
loses 3-5% across nodes; with readers it lost what the native lock loses,
because the readers of both nodes took the lock's lines back and forth and
nothing ordered them. For the rwlock there is a second reason: a reader that
meets a writer queues on `wait` without a continuation and ends the session
(1.4-1.8 sections per session with 20% writes, round 10), so the order of the
session rarely applies to anything. TCLock's rwlock does not lose because its
readers pass through the combining queue as well, which is served one socket
at a time; it pays for that within one node (4.97 against kd's 6.23 on c01).

An **era** (`kernel/kd_era.c`) gives the reader-writer families the same
property without putting readers into the queue: a lock under pressure
serves one node at a time.

```
era word of a lock (shared by hash, a line of its own):
    node served + 1 | jiffies of the last writer session that renewed it

queue head, after taking the write side (kd_rwsem_post, kd_rw_post):
    pressure = readers it found in the lock + callers queued behind it (up to 2)
    drain    = how long those readers took to leave
    average both over the last sessions
    if pressure >= kd_rw_era_press (2.25) and drain < kd_rw_era_drain_ns (5 us):
        start an era for this node, or renew the stamp of the one that exists

caller of another node that found the lock in use:
    reader: it met a writer            writer: its fast path failed
    (rwlock: neither with interrupts or bottom halves off)
    -> count itself as waiting, then poll the era word only (kd_rw_era_wait):
         era is ours, or ran out   -> go on as usual
         bound passed              -> take the era over, note how many of us waited
```

Three properties make it safe to leave on:

* **It is advisory.** The era never admits a caller the lock word would not
  admit, and a caller that ignores it is only slower. All of its state may be
  stale or lost to a race.
* **It exists only where it can pay.** The pressure threshold cannot be
  reached by two callers in all, and by a few only if most of them are at
  the lock at once, so a lock that two nodes merely share has no era. Neither
  have writers without readers (the session's own order does that job), nor
  locks with long read sections (drain average over 5 us), where the readers'
  parallelism is worth more than the lines. A queue head only starts or
  renews an era; one that is no longer renewed runs out within two ticks.
* **The lock's time is divided by callers, not by nodes.** Waiting callers
  count themselves in a line only they write; the bound of a waiter is
  `2 x bound x theirs / (theirs + ours)`, where *theirs* is how many callers
  of the era's node waited when it took the era. Equal numbers give the plain
  bound (`kd_rw_era_ns`, 200 us, for both families). A bound is never under a
  quarter of that: an era begins with the lock still full of the other node's
  callers, and its node gets nothing done until they have left. An rwlock
  waiter spins with preemption off, as it would in the queue; its wait ends
  at `need_resched()` like the rwsem's, and it does not wait at all with
  interrupts or bottom halves off.

A waiter never looks at the lock itself. One look per waiter, taking the era
over if the lock was idle, was tried (#77, #78) and removed: it ended the eras
of a node with few callers after a few microseconds, and with the time of the
look derived from the CPU number one node kept winning.

A reader that finds no writer is never held back, and no fast path looks at
the era. The rwsem's reader fast path did until build #80 (whenever two
readers were in). In-boot on #81, 32 workers: that check alone cost 3-12% on
one node, and across nodes the lock was faster without it (16+16 with 1%
writes 10.87 -> 12.17 Mops/s). What the queue heads measure costs 0-3% (rwlock
with 20% writes), and nothing with `kd_rw_era_ns=0`.

What it costs is order: a caller can be passed by later callers of the era's
node for at most twice its bound per acquisition. That is the same kind of
bound the session's NUMA order puts on a passed-over writer, and like the
reader phase it is a change in the area `AGENTS.md` lists as deferred, made
because the user asked for the cross-node behaviour of the rw families to be
addressed. The measurements, including the placements with unequal numbers
and what each step of the design fixed, are in
`bench/results/kdclaude/era-20261115-64cpu/`.

## 7a. Plain mode and delegation mode

Delegation pays off only while the combiner keeps finding the next waiter
queued: then the lock's data stays in one cache and a section costs the
combiner little more than its body. With a short queue the combiner outruns
its waiters, and every section costs a lock handover plus the transfer of a
continuation, which is more than the native lock pays.

* **Plain mode** is where a spinlock or mutex starts. A contended caller
  waits in the family's `*_slow` function, on its own stack, nothing
  published. For the spin class this is the native queued spinlock,
  including the pending waiter; a mutex caller spins in the queue while the
  holder runs and parks otherwise, as before. A waiter queued this way never
  combines, and a session ends at its node.
* **Entering.** A queue head samples how many waiters are linked behind it
  (`kd_q_depth`, once per 128 contended acquisitions of a CPU, while it
  still waits for the holder so that the walk delays nobody). At
  `kd_deleg_enter` (spinlock, 5) or `kd_deleg_enter_sleep` (mutex, 3) the
  lock goes to delegation mode.
* **Where the mode lives.** Spin class: the bit `KD_Q_DELEG` in the lock
  byte, which only the holder writes and a release clears. It travels with
  the head role (`HEAD_D`), also through waiters that do not take part, and
  a pending waiter carries it over. A contended caller reads it from the
  lock word it has just read anyway; while the byte is momentarily empty
  (between a release and the next head) it goes by what this CPU saw last
  for that lock. Mutex: the flag `KD_QF_DELEG`, which outlives single holds.
* **Leaving.** A session counts the waiters still queued behind it every 32
  sections and when it ends; below `kd_deleg_exit` (2) the lock goes back to
  plain mode.
* **rwlock and rwsem writers always publish** when they can
  (`kd_family.always_deleg`). There a session saves more than cache
  transfers: the writers it serves share one wait for the readers to leave.
  A depth threshold kept rwsem writers from delegating at all (measured).
* `kd_adapt=0` keeps every lock in delegation mode.

The thresholds were chosen by A/B in one boot. The break-even depth really
depends on the section length, which nothing measures: at 6 workers a
16-line mutex section gains 27% from entering at depth 3 instead of 4, while
a 1-line spinlock section entered at depth 3 or 4 loses 2-3% at 4 and 5
workers.

## 8. Nesting

When the section a combiner C_A is running for W meets a **contended** inner
lock B, C_A behaves like a TCLocks combiner: it becomes the waiter for B and
publishes the continuation it is running.

* Spin-class locks (spinlock, rwlock writer) have `_jit` entries (generated
  code calls these instead of the public ones). The fast path is identical.
  On contention `kd_nested_exit` stores the continuation (callee-saved
  registers, `rdi`, `rax`, `rsp`, flags) into **the current packet** — the
  same packet, no copy — sets `resume` to the generated-code address after the
  call, and returns to the executor with exit `NESTED`.
* The executor queues a node for B that points at that packet and the
  generated code after the lock call (`kd_spin_nested`, `kd_write_nested`,
  `kd_mutex_nested`, `kd_down_write_nested`). B's queue decides:
  1. B's combiner C_B claims the node and runs W's continuation onwards. At
     `unlock(B)`, C_A's node is resumed and C_A continues W's section in
     generated code from the state C_B left.
  2. C_A reaches the head of B's queue: it takes B, serves B's other waiters as
     a nested session (depth-limited), and continues W's section.
  3. B is a mutex/rwsem and waiting would require sleeping: W gets the
     continuation back with the call to B still pending (handback).
* The packet records the locks it is being executed for (`roots[]`, at most
  `KD_MAX_ROOTS` = 4, with `nroots`). If an inner executor meets the release of
  an outer root (`lock(A); lock(B); unlock(A); ...; unlock(B)`) it must not
  unlock it, because A is still held by C_A's session: it sets a bit in
  `released` and applies only the logical effects. C_A sees the bit when its
  node resumes and ends W's turn on A. To keep ordinary releases free of this
  check, generated code compares only against `kd_cpu.root`, and leaves
  generated code for a non-root release only when `kd_cpu.anc` (the number of
  outer roots) is nonzero.
* A handback from an inner executor propagates outwards through the node
  states: each level either keeps its lock (its root was already released) or
  passes it to W, and W resumes natively exactly once.

Bounds: `KD_MAX_ROOTS` = 4 session locks per continuation, `KD_MAX_DEPTH` = 3
open sessions per CPU. Beyond them the inner lock is only waited for (no
publication). The recursion runs on the combiner's wait stack, which is
sized for it; real stack use has not been measured.

## 9. Images and sites

* One immutable image per site, replaced whole. A site is the return address
  of a lock call; it is looked up with preemption off in a hash table of
  `1 << 10` buckets.
* Publication: the translator asks `KD_IOC_IMAGE_ALLOC` for executable memory
  (`execmem_alloc` + `set_memory_rox`), links the image for that address and
  loads it (`KD_IOC_IMAGE_LOAD`). The new site entry replaces the old one; the
  old image is freed after `synchronize_rcu()`. A waiter and a combiner are
  non-preemptible from lookup to resume, which is what makes RCU enough: no
  reference counts.
* Learning: each image has 64 learning reports (`KD_MISS_BUDGET`). A miss or
  frontier exit reports `ip`/`target` into a lossy 4096-entry event ring that
  the daemon polls.
* Lock API in a section: the kernel lists every `kd_` function generated
  code may meet with a class (release, sleeping acquire, spin-class acquire,
  or `KD_SYM_LOCAL`: never sleeps, call natively). A `kd_` function that is
  not listed is a frontier.
* Usefulness: every 256 executions (`KD_SITE_WINDOW`) a site whose sections
  were mostly handed back is switched off (`KD_EV_SITE_OFF`) until a new image
  arrives.
* `KD_IOC_ENABLE` is the global switch (static key `kd_delegation`). With
  delegation off every lock behaves as a plain queued lock.
* Text lifetime: an image copies text and embeds its addresses. A module
  notifier increments a text generation on module load and, when module
  text or init text is about to disappear, unpublishes every site, waits one
  grace period, frees all images and reports `KD_EV_TEXT_GONE`. A load
  carries the generation its image was built from and is refused if it
  changed, and a site must lie in live text. Fixup instructions are reported
  per text region (core or module) by `KD_IOC_TEXT`, so module exception
  tables are covered.

## 10. Invariants the code relies on

1. Exactly one participant advances a packet at a time: the origin before it
   queues, the combiner while the node is claimed, the origin again after
   `RESUME`. `RESUME` is the last access to the node and to the packet.
2. A queued waiter is non-preemptible and on its wait stack until resumed, so
   its node, packet and stack outlive every access by a combiner.
3. Handback never replays: the packet always names the next instruction to
   execute.
4. A combiner never sleeps in a delegated section; every call that can sleep
   is a frontier exit.
5. Lock word ownership is by value: after a handback the origin's ordinary
   unlock is the only way the lock is released.
6. `kd_cpu.busy` is set for the whole time a CPU's packet and wait stack are
   in use; interrupts that find it set wait without publishing.
7. Spin class: while a queue exists its head is the only possible taker of
   the lock (the fast path needs the whole word zero, a pending waiter only
   exists without a queue), so the head takes it with a plain store.
8. An offered head (`HWAIT`) changes state only under its table bucket
   lock, together with its table entry.
9. A task's RCU read-side depth is changed only by code running as that
   task.

## 11. Known limits

See also [DIFFERENCES.md](DIFFERENCES.md).

1. **Partly tested.** Boot, all four families with and without delegation,
   two-level nesting, handback through frontier and sleeping-acquire exits,
   module unload with live images: see [BUILD_AND_TEST.md](BUILD_AND_TEST.md)
   section 5. Deeper nesting, interrupt-context interactions, signals and
   hotplug are not tested.
2. **Handback inside a per-CPU-bound region.** If a section is handed back
   while it has preemption disabled beyond its locks (counted as
   `handback_pinned`), the origin continues on a different CPU than the code
   before the exit ran on. The preempt count is transferred; per-CPU pointers
   already taken are not.
3. **Flags across call/ret.** Return and indirect-branch dispatch clobber
   flags; the System V rule that flags are dead there is assumed.
4. **Text patching.** Images are built from live text. Later jump-label,
   static-call, ftrace or livepatch changes are not tracked.
5. **Module load/unload drops every image.** Correct but coarse: each
   module unload (and each module's init completion) causes all sites to be
   translated again.
6. **Unwinding.** No ORC data for images, the wait stack, the stack switch or
   the entry stubs (which now also call the plain slow path); stack traces
   through them stop early.
7. **Task fields updated through `current`.** Apart from the RCU depth
   (section 6), a section that updates a field of its task non-atomically is
   executed with that update made from the executor's CPU. If interrupt
   handlers on the origin's CPU update the same field, an update can be
   lost. No such case was observed besides RCU; `pagefault_disable()` and
   `migrate_disable()` in a delegated section are the candidates.
8. **Not delegated:** readers, trylocks, `raw_spinlock_t`, waiters in
   interrupt context. Native code called from a section that itself blocks on
   a lock waits without publishing.
9. **Nesting bounds** as in section 8; a release reached through a sibling
   `jmp` in a nested run is handed back.
10. **API coverage:** see [KERNEL_INTEGRATION.md](KERNEL_INTEGRATION.md).
