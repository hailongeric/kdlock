## C and W in the existing KD path

W means the original task whose source is stopped. C means the actual Linux task executing a borrowed fragment. W enters through the compiler-clobber macro with object, pre-CALL SP, post-CALL IP and BP. The transient preparation C call unwinds before `kd_mutex_entry_asm` moves hardware RSP onto W's preallocated auxiliary control stack. Only then can capture and publication expose W's original stack. W's ordinary wait/progress calls execute on that auxiliary stack, so they do not overwrite the source frames that C may access. These are two stacks belonging to one Linux task, not two schedulable tasks. [main include/kd_mutex_api.h:29-60, include/mutex_api.S:19-48, include/mutex_entry.S:18-40]

C accepts the exact `node->state` binding and enters the generated wrapper on C's own current native/control stack. The wrapper preserves C's native callee-saved registers. Source SP and BP are represented by mapped registers and W's one canonical packet. C's hardware RSP is not replaced with W's source RSP. Ordinary source CALL/RET words are read/written on the retained W stack through the existing lowering. [main include/wrapper.S:21-53, kernel/state.c:97-125, kernel/source_stack.c:13-28]

At a first-unexecuted native frontier, the current driver consumes/stages the exact exit and transfers W's single source binding to W's fresh native endpoint. W must actually be scheduled to accept that endpoint. W's auxiliary entry then finishes its exact actors and `kd_native_resume` imports canonical registers and moves hardware RSP to W's exact source SP. The temporary return word reaches its exact source IP. C can retain physical KD owner duties independently of that source transfer. This remains the existing immediate handback rule. [main kernel/episode.c:670-699,1095-1145, kernel/native_entry.c:163-207, include/native_resume.S:14-36]

Sleepable KD waits and owner pumps call Linux `schedule()` when appropriate. A stack switch itself does not cause that scheduling and cannot override an outstanding physical preemption pin. The existing source-family spin lane has its own physical depth reconciliation; that code does not supply a dynamic native PTL/RCU context lane inside a sleepable rwsem episode. [main kernel/mutex.c:285-306, kernel/episode.c:174-194, kernel/native_entry.c:133-160, kernel/episode.c:820-828]

## What the pinned TCLock switch actually does

TCLock W saves six native callee-saved registers and its original hardware RSP in its task node, then changes RSP to its own task shadow stack before entering its slow queue/wait logic. The full-kernel fork code cold-allocates an 8192-byte shadow stack and node for every task. The saved stack is an actual native compiled continuation, with the lock CALL return and source frames intact. [TCLock src/kernel/linux-5.14.16/kernel/locking/rwsem.c:747-835, kernel/fork.c:966-980, include/linux/mutex.h:55-84]

When C selects W, `execute_cs` writes W to **C's** `komb_curr_waiter_task`, saves C's current shadow-stack cursor and loads W's saved native stack. `komb_context_switch` only pushes/pops RBP, RBX and R12-R15 and exchanges RSP through two pointers. It contains no Linux scheduler switch, current_task write, GS-base write or CR3 change. Despite an IRQ comment, the actual switch body contains no CLI/STI operation. The pinned `current` macro still reads the physical CPU's `current_task`. Thus the executing task remains C while C runs native instructions on W's stack. [TCLock lib/combiner.c:12-40, kernel/locking/rwsem.c:338-369, arch/x86/include/asm/current.h:11-18]

At typed writer unlock, TCLock can save the completed W continuation and switch directly to the next waiter's saved stack, or back to C's saved combining stack. Completion/locked publication and wakeup allow actual W to leave its separate waiting control and return through the saved continuation later. The native waiter body has already reached its unlock under C before that completion is published. The source explicitly relies on the original node remaining active while its origin waits. [TCLock kernel/locking/rwsem.c:1007-1043,489-507; matching RCUHT locks/komb_rwsem.c:1197-1221]

TCLock's rwsem waiter loop can enable preemption and schedule, including its park/wake handshake. That is real scheduling of an existing task, distinct from `komb_context_switch`. The switch does not allocate another CPU or guarantee when W runs. [TCLock src/kernel/rcuht/locks/komb_rwsem.c:57-95,243-272]

The local Linux 7 module port adds a narrower admission/lifetime adapter. It requires exactly one allowed CPU per registered task and one registered task per such CPU. Its per-CPU context supplies the shadow stack and node, and retains each task until the whole cohort has actually exited and its context/queue/stack state is idle. These fixed-affinity restrictions are port requirements, not proof that pinned upstream allocates dedicated capacity. The port README excludes migration and oversubscribed/nested arbitrary bodies. [legacy master tclock_backend/rwsem_provider.c:56-105,170-188, rwsem_compat.h:21-46, README.md selected comparator scope]

## Why this matters at the actual Linux 7 PTL/RCU interval

The saved kernel8 emitted path reaches `__rcu_read_lock` at `81841237` before the PTL CALL at `8184159c`. RCU reads current_task at `81566f35` and writes that task's nesting field at `81566f4a`. Native raw spin acquisition changes the physical CPU preemption counter at `8276ccf5`; its PV slow CALL is at `8276cd2a`. Matching normal PTL/RCU calls are `8181e89a` and `8181e89f`. These are linked-text facts, not evidence that a live generated fragment executed them. [saved /tmp/kdlock-kernel8-mm-context-20261111-01/export/disassembly and source, manifest 78f6c172d5de54175c2d40459b4915bac2bc8e76fd4b9133b6880086c9e850e1]

TCLock's wholly native borrowed-stack interval would use physical C for native `current`, preemption and RCU operations throughout. That is internally different from KD's original backend, which maps the exact current_task MOV to logical W and maps other GS accesses through W's captured origin GS base. Translating RCU's nesting access would therefore address W while physical C remains the scheduler's participant. Translating a generic GS preemption-counter access can address W's capture CPU even if C is elsewhere. Merely switching hardware RSP cannot repair either distinction. [main disassem/backend/normal.py:39-58,110-120; include/wrapper.S:34-39; kernel/jit.c:692-713]

A common CPU can remove the spatial origin-GS versus executor-CPU difference for that interval if both tasks remain pinned there. It cannot make W run while C is nonpreemptible on that same CPU, and does not merge their task RCU nesting, current-derived state or exception paths. A same-mm check only constrains address-space identity. The current provider says so explicitly and performs no affinity reservation. [main tests/kernel/mmap_api/payload/mmap_jit_profile.inc:152-160]

The current four generic context boundaries remain pre-effect SPECIAL cuts. No PTL/RCU service is provided by that table. Returning W before those effects preserves the existing suffix path. Admitting an effect first would create a distinct obligation to keep the exact native section alive until its matching physical release has completed. Starting a new W RCU section and ending C's old one is not, by itself, continuous protection for pointers already observed under C's old section. [main tests/kernel/payload/native_context_boundaries.inc; saved kernel8 include/linux/rcupdate.h:801-824]

## Concrete alternatives and choices still required

| Execution arrangement | What consumes CPU time | What existing storage provides | Missing decision or mechanism |
| --- | --- | --- | --- |
| Current safe pre-context handback | Actual W runs its native suffix after C transfers the packet | W's auxiliary wait stack and retained original stack already exist | No new policy is needed when C has not entered unsupported native context |
| Actual W continues while C retains a nonpreemptible native section | C and W require concurrent physical execution capacity for the dependency interval | Existing W task and stack can be reused, so an extra helper task/stack is not inherently needed | Exact distinct CPU admission/reservation, scheduler progress assumptions, nested demand bound and failure behavior are unspecified; affinity alone is not capacity proof |
| C continues W's native body on a borrowed W stack, as TCLock does | One physical C executes the native body; W need not run for that interval | KD retains W's source stack, but its generated wrapper deliberately keeps C's hardware stack | A native borrowed-body continuation engine, native current/GS/mm/API semantics and precise entry/return/mitigation/exception contracts would be new work; retained stack bytes do not supply them |
| C services native context while current KD source execution/handback stays intact | C retains actual native duties and W executes source/native continuation under an explicit protocol | Exact KD owner/ACK records are a useful lifetime precedent | There is no generic native PTL/RCU token, paired release routing or context-aware non-sleeping owner pump today |

For the second arrangement, a concrete admission rule must identify actual C/W tasks, their allowed and online CPUs, how each accepted concurrent C duty leaves W a usable execution endpoint, and what interrupts, hotplug, scheduler delay and nested sections are assumed. Using spare CPUs already present differs from adding CPUs to the VM, but both consume capacity beyond merely retaining an auxiliary stack. The current code establishes neither rule. No count or CPU mask alone establishes bounded progress.

For any arrangement that allows W to progress while C holds a native section, native raw spin release must finish on the physical context that owns its preemption reference, and RCU release must close the actual retained read section. Exact acquisition identity, task/CPU context, object/pointer protection, nesting, release request, physical callback completion and callback-return lifetime need explicit ownership. W must not consume an accepted release and continue after the protected scope until the required physical ACK. There is no such generic pair protocol in the current native context table. The existing KD release code supplies exact owner-task-only callbacks and after-callback ACK publication only for its own KD lock batches. [main kernel/owner_progress.c:31-34,112-169, kernel/mutex_release.c:324-413]

Memory must retain W's original task and task stack, its one canonical core, exact node/frame/binding/parent-return users, generated code/source/image uses and both tasks' auxiliary/native control continuations until their final accesses and callback returns. Current KD explicitly obtains task-stack and task references and allocates auxiliary/slot/frame backing cold. Detach rejects live auxiliary entries, owner batches, native/source grants, images and request users. Its asynchronous cancellation finalizer is restricted to ungranted metadata and cannot free a stack underneath a native section or an owner pump. Neither task identity nor a `retirable` scalar alone owns allocation. [main kernel/source_stack.c:31-55,72-87, kernel/task_storage.c:24-41,63-111,288-348,432-467, kernel/task_state.c:157-217,220-245, kernel/request_pool.c:29-46]

The user-facing choice is therefore about who physically executes the continuation and how its native obligations progress. It is not a choice between an existing KD stack switch and an optional redundant stack. No one of these alternatives has been selected or implemented by this review. The safe pre-context handback remains in force.
