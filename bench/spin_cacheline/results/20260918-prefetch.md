# 2026-09-18：后继请求预取地址前移

普通和虚拟 waiter 在发布队列前准备实际寄存器包指针、受检栈地址和
FULL/complex 标记。combiner 从节点直接取得这些提示，先预热 frame，再预热
寄存器包及逻辑 SP/push 地址，无需先解引用下一请求的 frame、task 和 SP。
普通生产者直接提供内嵌包，虚拟生产者沿用被保留的父包；没有寄存器复制。
节点从 48 增至 64 字节，request 继续按原引用/owner ACK 规则独立存活。

实现见 [prefetch.inc](../../../kernel_module/spin/prefetch.inc)，
协议见 [DESIGN](../../../docs/design/frames.md#911-reuse-before-copy-contract)，
定向功能验证见[测试记录](https://github.com/hailongeric/kdlock/blob/1b9191256f64785f8e844ada914356a69d4f70f0/tests/README.md#spin-prefetch-hints)。

## 四路同环境对照

保留 `spin_native_cache=1`，使用同一 caller-clobber v1 工作负载与编译选项。
每组五轮交替，比较以下四臂：

| 名称 | 输入与含义 |
| --- | --- |
| before | 保存自提交 `7f62744` 的旧 provider，48 字节节点、原预取实现 |
| off | 新 provider，`spin_prefetch=0`，不执行后继请求预取 |
| lookup | 同一新 provider，`spin_prefetch=1`，保留 combiner 查地址的策略 |
| prepared | 同一新 provider，`spin_prefetch=2`，使用生产者准备的提示；新默认值 |

后三臂使用**相同二进制和 64 字节节点布局**，只有装载参数不同；0/1 不准备
新的提示。它们与 before 的差异还包含节点布局、策略分支和代码布局，不能
将 lookup 当成原旧二进制，或将 before 的全部差值归因于某次预取指令。
开关只控制 combiner 的后继请求预取，队列返回处已有的栈预取四臂均保留。

**120/120 场正确完成并排空，共 1 亿次完整操作。** 40 场单线程为 NO_JIT，
80 场竞争配置均有测量期实际 JIT。每线程十万次；表中为五轮中位吞吐，Mops/s。

20 线程的 prepared 相对同镜像 lookup 提高 14.56%/13.28%，相对 off 提高
14.02%/8.38%。相对旧版本则为 7.29%/9.34%；JIT 均约 99.8%，提升没有伴随
代理覆盖率的大幅下降：两种规模与旧版本的 JIT 中位比例相差不到 0.02 个百分点。
4 线程基本持平，prepared 相对旧版本的 JIT 比例反而略高，
不能当作固定代理量的服务成本比较。结果支持在本负载保留新默认值，不支持
“关闭预取总会更快”或“所有配置都提速”。

20 线程五次吞吐范围：1 cacheline 的 before 为 1.6011–1.6947，prepared 为
1.7192–1.8552 Mops/s；16 cacheline 分别为 1.6018–1.6432、1.7035–1.7719。
范围未重叠，但只有同一虚拟机内的五次，不是跨机器或长期稳定性证明。

短矩阵单线程每场只有约十毫秒，三个新模式在测量期都没有排队 JIT；其间
吞吐差异不能解释为后继预取收益。下面用较长运行单独检查完整原生成本。

## 结构验证与限制

guest `pahole` 确认节点为 64 字节：execution 位于 40，提示包指针位于 48，
提示 SP 位于 56，两个标记使用原 padding。`run_combiner` 反汇编确认 prepared
分支只从 node 读取这些字段；对 frame/包的访问在该分支中是预取指令，旧策略
的深层读取保留在另一分支。不可读页单元探针独立验证同一读取边界。

这消除了 combiner 为计算提示地址而进行的依赖读取，但生产者增加了准备与
存储工作；不是消除全部状态成本。没有逐 load 的周期隔离、cache-miss 事件
或本轮新硬件采样，不能把吞吐变化换算为某条指令的净延迟。保留原生 L/S、
source 生命周期、准入、完整中途物化和 owner/ACK，没有以少执行 JIT 换提速。

环境为 recovery guest `6.1.159-kdclobber1`，Build ID
`db937d722ee2f2668acb12dc6f105aeea33b7c5c`，40 vCPU、28 GiB、双 NUMA；使用
node 0 的 CPU 0–19。保留 frame pointer、缓解、watchdog、nokaslr、voluntary。
四臂均单 CPU 预热/晋升，发布后停止 daemon，再开始同一数据校验负载。
这不修复既有并发冷晋升问题。五次样本和虚拟 CPU 环境不保证其他负载的收益；
本轮没有跨 NUMA、任意 task/per-CPU 临界区或全量回归。

## 复现与证据

运行器基于既有 `bench/tclock_compare/run.py` 的完整会话与 oracle，仅增加
旧 provider 切换和模式参数/读回检查；冻结脚本保存在本次外部证据的 `compare.py`。
先保存旧 provider 与源码到 `before/`，再同步新源码；不能把两个版本在运行中
互相覆盖。以下命令仅在遵循[操作手册](../../../docs/AGENTS.md)的 recovery guest
中运行，使用固定依赖 venv、KDIR、已确认快照及外层 timeout，输出目录必须新建：

```sh
python3 /root/kdlock-evidence/spin-prefetch-20260918/compare.py \
  --output /root/kdlock-evidence/spin-prefetch-repeat/compare --abis clobber \
  --kernel-source /root/linux-6.1.159-kdclobber1 \
  --kernel-baseline /root/kdlock-kernel-baselines/spin-clobber1-20260918
# 长批次另选新 output，并加：
# --backends before prepared --threads 1 --iterations 10000000
```

原始证据在 guest `/root/kdlock-evidence/spin-prefetch-20260918/`。宿主归档为
`/tmp/kd-spin-prefetch-20260918/evidence.tar.gz`，17,516,728 字节；与 guest 的
SHA256 一致：`056b90f37fcb8d374d52b0b97724a10b2e6b89bfba3dd1bdde6cbb9409a35188`。
保留源文件、二进制、kernel baseline、逐场参数、生成物、IRQ/preempt/数据检查、
实际 JIT、退休与排空，以及首次构建失败、定向测试和节点/汇编检查。

文档在测量后补记，不代表重跑。
