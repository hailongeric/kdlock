# 2026-09-20：对齐 RCUHT 的 IRQ 检查及模块 UBSAN 设置

按用户选择，关闭 TCLock 的 IRQ 检查和 TCLock/直接负载模块的 UBSAN 插桩，
不重建内核。六场小样例及 Linux/TCLock 正式 **50/50 场全部正确完成并排空**。
正式测量共 49000000 次操作；四线程 TCLock 为 Linux 的 **0.842×**，
8/16/20 线程分别为 **1.422× / 1.567× / 1.583×**。

关闭这两项检查后，四线程仍有退化。较高线程数的委托收益保留，本次没有复现
论文环境，也没有独立测出 IRQ 检查和 UBSAN 各自的成本。

## 修改及生效证据

- [komb.h](../../../tclock_backend/include/spinlock/komb.h) 不再定义
  `ENABLE_IRQS_CHECK`，对齐上游 RCUHT；不打开 `KERNEL_SYNCSTRESS`，等待循环
  仍为原有纯轮询。只适用于当前 IRQ 开启、task 上下文的单锁样例。
- [TCLock Makefile](../../../tclock_backend/Makefile) 设置 `UBSAN_SANITIZE := n`。
  [负载 Makefile](../../../workload_modules/spin_cacheline/Makefile) 对
  `SC_BACKEND=native|tclock|kdlock` 同样关闭 UBSAN；不指定直接后端的普通测试
  构建仍继承内核配置。未修改 kdlock provider 的插桩配置。
- IRQ 检查关闭后，原局部变量只在 debug 检查中使用，增加 `__maybe_unused`
  消除新告警；`port.patch` 同步记录。没有改动队列、换栈、WWJUMP、预取、
  NUMA、完成计数、批次额度和调度退出规则。
- [运行器](../run.py) 检查实际模块的未定义符号，不允许带 UBSAN handler 的
  TCLock 或直接负载进入测试；额外保存后端反汇编。后端与负载构建日志使用
  不同文件名，避免覆盖。

对修改前后 ELF 的检查结果：

| 检查 | 调整前 | 调整后 |
| --- | --- | --- |
| TCLock 上锁/解锁中的 IRQ flags 读取重定位 | 各 1 处 | 均为 0 |
| TCLock 上锁/解锁中的 UBSAN handler 引用点 | 4 / 2 | 0 / 0 |
| TCLock 后端未定义 UBSAN handler 符号 | 有 | 无 |
| native/tclock/kdlock 三种直接负载 UBSAN handler | 前轮 native/tclock 有 | 本轮三种均无 |
| TCLock context switch 的 return thunk | 保留 | 保留 |

TCLock 和两种实际测量负载的编译命令均确认没有 `-fsanitize`。kdlock 直接
哈希表负载另行构建成功，并确认无 UBSAN 引用，但未加载或计时。
**运行内核的 UBSAN 仍开启，原生 qspinlock 对象仍有 UBSAN 引用。** 这是用户
选择的模块级范围，不能标为整个内核已对齐上游配置。

## 五轮中位数

单位 Mops/s，越大越好。每轮后端交替排列，未选择最快样本。

| --- | --- | --- | --- | --- |
| 1 | 14.113 | 13.511 | 0.957× | 0.946× |
| 4 | 2.972 | 2.502 | 0.842× | 0.876× |
| 8 | 3.026 | 4.304 | 1.422× | 1.335× |
| 16 | 3.111 | 4.876 | 1.567× | 1.564× |
| 20 | 3.163 | 5.005 | 1.583× | 1.571× |

本轮四线程比 Linux 低 15.8%；Linux 五轮范围 2.689–3.024，TCLock 为
2.427–2.596 Mops/s。20 线程范围分别为 3.146–3.427 与 4.948–5.129 Mops/s。
上轮数据见 [9/19 哈希表记录](20260919-rcuht.md)。

| 线程 | 实际代理占比 | 每批代理次数（各场比例的中位数） |
| --- | --- | --- |
| 1 | 0% | 无代理批次 |
| 4 | 59.42% | 2.00 |
| 8 | 99.27% | 260.49 |
| 16 | 99.83% | 834.98 |
| 20 | 99.84% | 849.17 |

四线程仍只有约两个请求/批，换栈和交接的固定成本难以摊薄，与其相对劣势
相符。这是结合计数与算法作出的解释，不是本轮独立测量的周期成本。

Linux 和 TCLock 的绝对吞吐都比上轮高。两轮没有交替运行旧/新二进制的同期
控制组，也没有宿主 CPU 频率/调度的全过程记录；此外，两种旧负载的
`sc_body_0` 中本来就没有 UBSAN handler 引用。因此，**不能把绝对吞吐的
近两倍变化全部归因于本次检查关闭**，也不能从这里拆分两项改动的贡献。
本轮内部的 Linux/TCLock 倍率与正确性结果有效；跨轮列用于描述观察结果。

## 配置与验证

- 单全局锁哈希表：1024 桶、4096 节点、8192 键范围、100% 写请求，锁外
  `need_resched()`/`cond_resched()` 和四组乘加保留。哈希表正文、循环、客户端、
  直接 API、context.S、provider.c 与上一轮冻结源文件逐字节相同。
- 1/4/8/16/20 线程，每线程 100000 次，各五轮。每场单线程 48000 次预热，
  静置两秒；TCLock 批次参数仍为 1024，执行计数仍启用。
- 同一 `6.1.159-kdclobber2` 内核，Build ID
  `5ca28058e156f34a2c7fe91e8e0fbf92f4e51960`；voluntary，guest CPU 0–19。
  本轮没有调整宿主亲和性、缓解配置或内核。加载前核实
  `pre_static_boot_20260915` 恢复快照存在。
- 基础两项 C 测试、实际换栈续点测试及三项直接运行器/结果检查通过。
  换栈测试验证六寄存器、RSP、获取返回及代理 unlock 续点。
- 六场 smoke 覆盖 Linux/TCLock 的 1/4/20 线程，每线程 10000 次，共 500000
  次计时操作；正式 50 场另行运行，不混入汇总。
- 正式结果逐场核对全部迭代、哈希表结构、三类结果总和、IRQ/preempt 状态、
  代理 unlock/完成计数相等和最终排空。20 个竞争 TCLock 场均有实际代理。
  最终 workload、TCLock 和 kdlock 模块均未加载。
- 初次构建的未用变量告警已修正；既有自定义换栈的 objtool 栈/帧指针告警
  仍保留，没有屏蔽。未运行全量测试、未启用 mutex JIT、未提交 Git。

kdlock 的动态链表地址准入问题未修改。本次只验证它的负载可以无 UBSAN
构建，没有重复已知被拒绝的性能场景，不能称为三种锁性能全部通过。
