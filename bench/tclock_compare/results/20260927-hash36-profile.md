# 2026-09-27：36线程hash采样与有界批次调优

基点为`91553d0`。本轮只保留KD代理上限及独立NUMA扫描预算从512到1024的调整，
同步provider、benchmark构建和运行器默认值。TCLock、Linux、hash正文、JIT、wrapper、
CPU/lock热度、预取距离及内核均未修改。1024仍是精确的正文上限；延期远端链仍在最终
交接时优先，无新增每请求状态、锁、时钟或采样。它限制工作量，不保证调度延迟或无饥饿。

## 为什么36线程仍慢

### 准入不是主要原因

上一轮默认512的36线程KD峰值为1.835 / 1.837 / 1.845 Mops/s，
整段实际JIT占比99.635%–99.803%，node1完成份额49.898%–49.996%。
TCLock同期最高2.648 Mops/s，差距约30%。这些是[refill归档](20260927-spin-refill.md)的
历史数据，本轮没有重跑旧版KD对照。仅有较高JIT比例不表示代理执行成本接近原生正文。

同一历史配置16线程在node0时KD/TCLock峰值为3.500/4.703，
36线程跨node0/1时为1.845/2.648。单node已存在明显差距，不能全部归因于跨NUMA。
线程数与放置同时变化，也不能把这个比值当成隔离的NUMA延迟测量。

### hash放大了依赖读取与执行开销

负载具有1024个64-byte bucket、4096个64-byte node，合计约320 KiB数据，不是一个cacheline。
桶查找和链表遍历包含依赖指针加载。代理批次结束后，更换combiner可能需要重新取得
这些数据的缓存副本和被修改行的所有权；这与单cacheline正文有不同的成本比例。
更长批次提高吞吐支持“交接/局部性成本可摊销”的判断，但没有直接测量每次跨socket迁移延迟。

源正文相同不等于三方生成的机器码相同。TCLock的caller把源/目标key和bucket等保留在寄存器，
KD的clobber接口让编译器将它们放入waiter栈；JIT还需逻辑寄存器映射、预算检查和出口协议。
当前KD源链循环12条源指令变为15条：额外DEC/JZ及一次逻辑R11加载。
目标链的5条源指令变为9条，包括两个块的预算检查。原有frame/packet准入和退休也继续存在。
这些是静态指令差异，不等于每个请求固定多付相同的时间。

现有producer hints已在执行当前正文前预取下一请求的frame、寄存器包和waiter栈。
hash caller的统计对象位于逻辑SP以上约144字节，当前四个向上地址覆盖该区域；
锁外/栈上输入并非完全没有预取。更远node预取及请求前缀改读预取已有
[无明确收益的历史实验](20260927-hash-optimization.md)，本轮未重复堆叠hint。

### 新采样证据及限制

在未修改的`91553d0`、kernel UBSAN、batch512、NUMA-on下，三方36线程各三轮单独诊断。
使用guest中的perf 5.15.209，对实测client及继承worker以`cycles -F 499`采样；
不更改内核、不安装系统软件。所有9场业务/上下文/排空检查通过，lost samples均为0。
记录只有IP/TID/TIME/PERIOD，不含callchain；与普通性能结果分开，`performance_result=false`。
采样会扰动时序：KD诊断峰值约1.79–1.80 Mops/s，不取代未采样成绩。

离线使用同场kallsyms、冻结ELF的确切符号大小及实际JIT地址/长度归属采样；
未知地址保留unresolved，主要是用户态client代码，不把它们归给最近的内核函数。
采样权重除以该场完成操作数，得到以下诊断量：

| 范围 | 三轮 sampled cycles period / operation |
| --- | ---: |
| KD整个生成镜像（含wrapper） | 954 / 1038 / 1040 |
| TCLock原生`sc_body_0` | 763 / 736 / 724 |
| KD `run_combiner` | 312 / 346 / 333 |

这是带采样误差/skid的事件period估计，不是函数隔离计时，也不是精确cache-miss或load-latency事件。
KD生成镜像最热位置紧邻链节点value加载；TCLock原生正文也集中在相应遍历位置。
KD约92.9%–93.9%、TCLock约94.3%–94.4%的worker采样权重落在等待循环：
多数CPU在等待串行临界区，这是结果，不能仅凭热点百分比把PAUSE本身认定为根因。
本轮没有PMU cache-miss或跨node内存延迟的直接归因。

最终hash生成镜像未发现MFENCE/LFENCE/SFENCE或LOCK前缀指令。普通完成路径没有
每正文的完整硬件栅栏；锁字/ticket仲裁以及batch source lease仍在外部协议中。
删除x86上的acquire/release注释或编译顺序约束不等于省去硬件fence，且会破坏发布契约。
本轮保持这些顺序，没有以近似统计原则替代owner/ACK或存储生命周期。

## 独立候选

1. 在原代码上仅显式选择batch1024，16/36线程三方各三轮，共18场。
   KD16峰值范围3.685–3.708、36为1.965–1.970 Mops/s；TCLock36为2.632–2.637。
   相对历史默认512，36线程峰值约提高6.8%，仍未达到TCLock。
   含预热的整个会话平均batch从264–337正文增加到510–587；这不是实测窗口专属batch统计。
2. 单独试验简单直接CFG中让唯一虚拟GPR常驻物理R15，消除每次循环重载。
   修改值仍在块边界写回，wrapper重入从packet加载，间接/复杂映射保留原路径。
   基础与相关wrapper测试通过，但相同kernel/512下16线程仅3.471–3.488、
   36仅1.831–1.835 Mops/s，没有性能收益。候选和专用测试已撤回，源码/补丁/测试日志归档。
   这不能证明所有寄存器优化都无用，但当前不能以静态减少指令声称吞吐提升。
