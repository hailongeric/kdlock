# 2026-09-19：哈希表临界区对比

已将正文换成 TCLocks RCUHT 的哈希表查找、键值更新和节点搬移逻辑，并按用户
选择加入上游锁外调度点，保留原有四组乘加。**Linux/TCLock 的 50/50 场正式
测试正确完成并排空，共 49000000 次操作。** 四线程 TCLock 比 Linux 低 12.4%，
8/16/20 线程分别达到 Linux 的 1.34/1.56/1.57 倍。

kdlock 的哈希表正文被当前地址分析拒绝，未获得有效 JIT 成绩；不能把本次结果
称为三后端全部通过，也不能用旧 cacheline 成绩补入这张表。

## 五轮中位数

Mops/s 越大越好；ns/op 为所有线程总 wall 时间除以总操作数，不是获取锁延迟。

| 线程 | Linux Mops/s | TCLock Mops/s | TCLock / Linux | Linux ns/op | TCLock ns/op |
| --- | --- | --- | --- | --- | --- |
| 1 | 6.632 | 6.272 | 0.946× | 150.78 | 159.43 |
| 4 | 1.713 | 1.500 | 0.876× | 583.79 | 666.53 |
| 8 | 1.608 | 2.147 | 1.335× | 621.83 | 465.73 |
| 16 | 1.597 | 2.498 | 1.564× | 626.19 | 400.35 |
| 20 | 1.605 | 2.522 | 1.571× | 622.88 | 396.55 |

四线程样本有波动：Linux 为 1.632–2.811 Mops/s，TCLock 为 1.460–2.214 Mops/s；
表中保留五轮中位数，没有挑最快样本。20 线程范围分别为 1.582–1.615 与
2.507–2.542 Mops/s。

TCLock 的实际批处理（每场算比例后取五轮中位数）：

| 线程 | 实际代理占比 | 每批代理临界区数 |
| --- | --- | --- |
| 1 | 0% | 无代理批次 |
| 4 | 55.58% | 2.11 |
| 8 | 96.69% | 44.11 |
| 16 | 99.79% | 762.20 |
| 20 | 99.84% | 808.51 |

相较此前四线程 cacheline 负载的 1.06–1.31 次/批，本次批次变长；8 线程以上
实际代理比例明显提高，与收益开始出现的趋势一致。临界区和调度点同时变化，
本次无法将收益分别归因于其中一项。所有配置约 25% 成功更新/搬移、25% 目标
冲突、50% 源键缺失；这些都是完成的写请求，不把吞吐误记为成功搬移数。

## 负载与环境

- [正文实现](../../../workload_modules/spin_cacheline/hash_payload.h) 改编自上游
  `bbfb9f00a12af51dff6ca291cb9829a82960c2ef` 的
  `src/kernel/rcuht/rcuht.c:rcuhashbash_write_lock()`；原始 rcuhashbash 作者为
  Josh Triplett。保留查找、同桶更新、目标冲突、删除/插入和三类操作统计逻辑。
- 一把全局锁，1024 桶、4096 节点、8192 键范围、100% 写请求。桶和节点统一为
  64 字节步长，预分配于模块静态区域；临界区内不分配/回收。每个 worker 按 CPU
  固定种子生成 xorshift64* 随机键，与上游的分配布局和随机数发生器并不相同。
- 三后端编译相同正文，分别使用 Linux 原生、`komb_spin_lock/unlock` 和 kdlock
  clobber-v1 直接 API。没有调整锁协议、批次上限、缓解措施或准入规则。
- 每线程 100000 次，1/4/8/16/20 线程，各五轮，奇数轮反向排列后端。
  每场单 CPU 48000 次预热，静置两秒；准备不计时。预热后的哈希表继续用于测量。
- 一次 ioctl 包含完整 worker 批次；随机键、锁外 `need_resched()`/`cond_resched()`、
  四组乘加和循环均计时。调度点在解锁后、物理调用者恢复自己栈的轮次边界执行。
- 内核 `6.1.159-kdclobber2`，Build ID
  `5ca28058e156f34a2c7fe91e8e0fbf92f4e51960`，voluntary 模式。guest CPU 0–19
  均属于 node 0；每场绑定前 N 个 guest CPU，不宣称宿主物理核独占或复现论文机器。

每次计时外快照检查节点地址、回链、无环、桶归属、唯一键和完整 4096 节点集合。
各线程必须完成全部迭代，每次操作恰好计入一种结果；检查 IRQ/preempt 状态、
实际代理计数与完成发布相等、最终锁/队列排空。20 个竞争 TCLock 场均有真实
代理正文。最终测试模块全部卸载。

## kdlock 准入限制与小样例

`smoke02` 的 kdlock 在准备阶段返回 native-only。拒绝指令位于
`sc_body_0+0x15e`，即 `hlist_add_head()` 更新原头节点 `pprev` 的写入：

```text
MOV QWORD PTR [RAX + 0x8], RSI
CONTEXT_ADDRESS_WIDENED: address_candidate="kd_wide_RAX + 0x8"
CONTEXT_NATIVE_ONLY
```

这是动态链表指针写入分析后的地址不确定，不是已证明运行时访问非法地址。
日志的分析工作量为 1232/1000000，没有耗尽总工作量上限。运行器按现有要求拒绝
将 native-only 记为 JIT 通过，随后成功退休和排空。没有修改分析器、删准入检查
或换一种数据结构来制造通过；该场没有进入计时阶段，其余 kdlock 性能场未运行。

基础两项测试、三项直接对比/哈希结果校验测试，以及客户端批次 ioctl/时钟数量
检查通过。旧客户端 fixture 写死 ABI v1，首次失败后改为共享的 `SC_VERSION`，
相关测试复跑通过；新 layout ABI 为 v2。`smoke01` 在首场加载前按 STOP 边界
停下；`smoke02` 的 Linux/TCLock 单线程通过、kdlock 准入拒绝；`smoke03` 的
Linux/TCLock 1/4 线程四场通过，之后运行独立 50 场正式矩阵。没有自动重试
kdlock 拒绝，也没有把这些小样例并入中位数。
